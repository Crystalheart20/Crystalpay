# CoVest (AjoApp) project notes

## How to work with the owner
- He is a novice developer. Work ONE step at a time and explain what each command does, piece by piece.
- He uses Windows with Git Bash. Edit files directly yourself instead of asking him to find and replace blocks.
- Ask before running `gcloud run deploy`, `git commit` or `git push`. Never deploy or push on your own.
- After editing, confirm the file is saved and tell him how to check it.
- Never open, print or commit `env.yaml` or any `.env` file (they hold the Gemini key).

## What this is
Rotating-savings (Ajo) platform for a real group of members, plus real estate pools and a Relief Fund.
Real members and real money are involved: be careful, and never delete data in the `members`, `months` or `groups` collections.

## Stack
- Front end: React + Vite + Tailwind, in `src/`. Main state and Firestore handlers are in `src/App.tsx`. Types are in `src/types.ts`.
- Components in `src/components/`: Dashboard (admin), BallotWheel, ReceiptVerifier, WhatsAppSimulator, MemberPortal, RealEstatePools, AdminLogin, ReliefFund.
- Server: `server.ts` (Express). It serves the built site and two Gemini endpoints: `/api/verify-receipt` and `/api/generate-summary`.
- Data: Firebase Firestore and Firebase Auth. Project `concentrated-drummer-7wh20`. The Firestore database is NOT the default one: its id is `ai-studio-8b55aa2d-6f9d-411c-92b7-1ca158726564` (see `src/firebase.ts`).
- Security rules: `firestore.rules` in repo is the source of truth (copy-paste to Firebase console → Firestore → Rules to publish). All collections require `request.auth != null` (any signed-in session — anonymous counts, so Member + Admin portals keep working) and the catch-all is `if false` (deny by default). See `src/firebase.ts` anonymous sign-in.
- The separate `ajo-app` repo (Next.js/Supabase) is an unfinished scaffold. Ignore it.

## How things work
- Admin: Firebase email/password login, allowed only for the emails in `ADMIN_EMAILS` (App.tsx and AdminLogin.tsx). Everyone also signs in anonymously so Firestore rules can require a session.
- Members use the link `?role=member&groupId=default`. They log in with email and password (linked through `member.authUid`) or the older PIN fallback.
- New self-registered members start Pending (`isActive: false`) and cannot be drawn in the ballot until the admin switches them to Active in the Dashboard.
- Rounds are months with ids like `2026-06`. The rotation runs June to December 2026. Mid-cycle joiners should not win this cycle.
- Receipts: if the Gemini check fails or the key is missing, the server returns FLAGGED / `MANUAL-REVIEW` (never a fake approval). Status 402 means the prepaid credits on the CoVest AI Studio project ran out.
- Contributions (winner-then-admin flow, done 2026-10-17): member uploads receipt → saved as `PENDING` (`status` on PaymentLog, see types.ts). Winner sees it in MemberPortal "Incoming Credits" and clicks Confirm Credit (`confirmedByRecipient`). Only then does the admin's Dashboard "Final Confirm" enable; it stamps `CONFIRMED` + `adminConfirmedAt/By`. Dashboard Collected Pool and Transfers Cleared count only `CONFIRMED` (old payments without `status` count as CONFIRMED for backwards compat). MemberPortal shows Awaiting winner + admin until confirmed.
- Member inner tabs (done 2026-10-19): `MemberPortal.tsx` uses `memberTab` state (overview / recipient / upload / confirm / ledger / relief). Pre-draw (`isDrawDone=false` when `recipients.length===0`) shows only Overview/Ledger/Relief and "Awaiting ballot" message; post-draw, sender gets Recipient+Upload, receiver gets Confirm; boxes hidden via `hidden` class to preserve form state.
- **Silent upload failure, found 2026-10-31 (live bug, fixed in code, needs deploy)**: the winner of `default_2026-10` saw only ONE payment while members had uploaded AI-approved receipts. Cause: `onPaymentApproved`/`handleRecordPayment` swallowed the Firestore error (`catch { console.error }`), and the uploader was signed in ANONYMOUSLY at that moment (PIN login, member link, or a page reload — see the `firebase.ts` note), so the published rules (`isMemberOf` → `groupRoles/{groupId}_{uid}`) rejected their write to `months`. The member still saw the green "⏳ Sent!" panel. Not a "no email account" problem only: Bamisaye and Raimat both have email logins and matching role docs, yet their uploads were still refused because the browser was not holding that email session. Fix: `handleRecordPayment` now returns `{ok, error}` and rolls back its optimistic ledger entry on failure; MemberPortal and ReceiptVerifier `await` it and show a red "not saved" message; the Upload tab shows an amber "create your email login first" notice and disables the Audit button whenever the browser's Firebase user is anonymous or is not the member's `authUid` (checked live via `onAuthStateChanged`). Also `src/firebase.ts` now calls `signInAnonymously` only when nobody is signed in (`auth.authStateReady()`), so a page reload no longer replaces a member's email session with a fresh anonymous one — that reload was the reason even email members could lose write rights mid-session.
- **Rule to remember**: any member-side Firestore write can be refused for a PIN-only/anonymous session. Never show success unless the write resolved without error.
- **Startup order matters (2026-10-31)**: because `firebase.ts` now waits for `authStateReady()` before signing in anonymously, every App-level Firestore listener (groups, members, months, the 2026-06 auto-seed) is gated on `authUser` (`if (!authUser) return;` plus `authUser` in the deps). Without that gate the queries fire before the anonymous session exists, the rules refuse them, and `onSnapshot` does not retry — the app stayed empty with "Missing or insufficient permissions" until a reload. If you add another listener in `App.tsx`, gate it the same way.
- **Member logins panel (2026-10-31)**: `src/components/MemberLoginsPanel.tsx`, rendered in the Admin Control Panel right after `MigrationPanel` (visible to the platform admin and to group heads). It lists each member's `email` + short `authUid`, flags the ones with no login yet, and has "Copy" and "Send reset" per row. "Send reset" calls `sendPasswordResetEmail(auth, email)` — Firebase mails the reset link, so **nobody can read a password**; that is the only way to help a member who forgot it. A member who says they made an account but shows "PIN only" has no email on their profile: their account, if it exists, is only visible in Firebase console → Authentication → Users.
- House rule: always update this CLAUDE.md file whenever you change how the app works, so the next session starts with the truth.

## Groups, roles and group heads (step 1, 2026-10-20)
Goal: let strangers create their own groups, each run by its own group head, without the CoVest operator touching every group.
- Roles live in a new collection `groupRoles`, one document per person per group: `groupRoles/{groupId}_{uid}` = `{ groupId, uid, email, memberId, role }`, role = `MEMBER` | `HEAD`. `src/groupAccess.ts` holds `roleDocId()` and `ensureGroupRole()` (create-only — the rules forbid editing a role).
- Three tiers: **platform admin** (the `ADMIN_EMAILS` address, all groups), **HEAD** (admin powers inside one group only), **MEMBER** (may only write records that are their own). `Member.role` and `AjoGroup.status/createdBy` were added to types; `AjoGroup` is still declared in App.tsx.
- `firestore.rules` was rewritten the same day. WRITES are now group-scoped and role-checked: only the platform admin or the group's HEAD can write months/payments/relief balances, members can only write their own pending relief records and only toggle `payments` / `payoutConfirmedByRecipients` on a round. READS are still `isSignedIn()` — scoping reads needs group-filtered queries everywhere and is step 2.
- A member's login must be a real Firebase account before they can transact (relief deposits/withdrawals/requests/votes/repayments, and their own confirmations). PIN-only members are listed by the migration panel and must register with email + password first — MemberPortal shows an amber notice on the Relief tab for them.
- Self-registration now writes a role document after the member document (`ensureGroupRole`). The PIN → email upgrade ("Set up email login") uses `updateDoc` (only `email` + `authUid` change) and then claims the role. `createUserWithEmailAndPassword` is followed by `getIdToken(true)` so Firestore signs the write with the new account, not the old anonymous session.
- Relief voting is now two writes, not one batch: the receipt (`reliefVoteReceipts/{requestId}_{memberId}`, create-only) first, then the anonymous ballot — the rules require the receipt to exist before a ballot can be written, which is what stops a second vote.
- **Order of operations when publishing**: deploy the new code → paste the new `firestore.rules` into the Firebase console and publish → open the Admin Control Panel → run the "Step 1 — Role & group migration" panel once (stamps `groupId` on any document missing it and creates a role document for every member that has an email login). The migration has to run *after* the rules are published: the old rules deny every write to `groupRoles`, so under them the migration can only stamp `groupId`, not create roles.
- **The role document is re-claimed on every sign-in** (`handleMemberLogin` calls `ensureGroupRole`), so a member who registered before the rules were published gets their role the first time they log in again. `ensureGroupRole` never blocks a member over a failed role write — it logs a warning and the next sign-in fixes it.
- **Pilot status (checked 2026-10-20)**: of the 7 members in the "default" group, only ONE has an email login. The other six sign in with a PIN, so after the new rules are live they can browse but cannot confirm payments or use the Relief Fund until they set up an email + password (the portal prompts them right after their PIN login). Drive that before the round closes.
- **Testing the rules before publishing**: `python tools/rules-test.py` compiles `firestore.rules` and runs ~60 behaviour cases against Google's Rules API (`firebaserules.googleapis.com/projects/<id>:test`) without touching the live project. It needs `gcloud auth print-access-token` to work. Suite A runs the real rules; suite B runs a copy with the role lookups stubbed, because the test API has no document store (`exists()` on another document always fails there) — that is what lets the field-level guards be checked on their own. Run it after every change to `firestore.rules`, before pasting the file into the console. It is the only way to catch a broken ruleset without a publish attempt.
- **Rules gotchas, learned the hard way (all three cost a publish attempt or a live bug)**:
  1. Reading a field that is not there is an ERROR, and an error denies the whole request. `request.auth.token.email` on an anonymous session errors, so `isPlatformAdmin()` checks `"email" in request.auth.token` first, and every optional field is read through a helper (`groupOf`, `authUidOf`, `statusOf`, ...) that returns null instead of blowing up. The helpers must also survive a NULL map (a document that does not exist).
  2. A path segment may hold only ONE `$(...)`. `.../$(a)_$(b)` does not compile — build the id in a function and interpolate that.
  3. `endsWith()` is NOT a Firestore rules string method (it compiles, then fails at runtime). Use `docId.matches(".*_" + request.auth.uid + "$")`.
  4. A person must be able to READ their own role slot before it exists, or they can never claim it — the read rule matches on the document id as well as the uid field.
- **The member portal's session is not the Firebase session.** "Logging in" to the portal (member link, PIN, or the saved session in localStorage) only sets `ajo_member_session`; the browser is still signed in ANONYMOUSLY. The rules judge a write by the Firebase uid, so a member who browses through a link or a PIN cannot write anything. The member portal must therefore use the email + password form, and the app claims the role document (`groupRoles/{groupId}_{uid}`) whenever a real session appears — in `App.tsx`, the `claimedRoles` effect, for the member record belonging to the group being VIEWED (one person has one member record per group).
- **`createGroupAsHead` is the self-service path** (member portal → "Start my own group"): it writes the group (`status: PENDING_REVIEW`, `createdBy` = the founder), the founder's member record inside that group, and their HEAD role document. The founder can rename the group, withdraw it while it is pending, and can never approve it — that is the operator's job (Admin Control Panel → "Group requests").
- **Known gap — profile claiming**: a member record that has no `authUid` yet (a PIN-only member) can be claimed by anyone who knows its document id, because the rules cannot verify that the claimer is the person the profile belongs to. It only bites while reads are unscoped (see gap 3). The fix, for step 2: keep a hash of the PIN on the member record and have the claim write carry a hash of the PIN the member typed, so the rule can compare them — and move PIN checking off the client at the same time.
- **The rules are published (2026-10-20)**. The live release is `projects/concentrated-drummer-7wh20/releases/cloud.firestore/ai-studio-8b55aa2d-6f9d-411c-92b7-1ca158726564` — note the database id in the release name, this project does NOT use the default database. To republish without the console: create a ruleset (`POST /v1/projects/<p>/rulesets` with the file as `source.files[0].content`), then point the release at it (`PATCH /v1/projects/<p>/releases/cloud.firestore/<dbId>` with `{"release": {"name": ..., "rulesetName": ...}}`), using a gcloud access token plus the `x-goog-user-project` header. Then confirm the live file matches the repo file by fetching the ruleset back.
- **Rollback**: the previous rules are saved as `firestore.rules.v1-backup`. If the new rules turn out to be too strict, paste that file back into the console and the site goes back to permissive rules immediately (no data is lost either way — the rules only control who may write).
- The rules are pasted into the Firebase console by hand, so a syntax error is caught at publish time and the old rules stay in place. Publishing is the risky moment, not deploying.
- Migration panel lives in `src/components/MigrationPanel.tsx`, rendered at the top of the Admin Control Panel. It only ever adds fields, so it is safe to run twice.
